# 可行性评估：能不能「完全按小说来」做 2.0

> 讨论记录 · 2026-09-27 · **本文是设计结论，不涉及任何代码改动**
> 对应问题：「如果完全按照小说的模式来设计游戏，能不能实现，实现不了的是什么」
> 配套文档：`设定溯源.md`（原著设定清单）、`DEVLOG.md`（数值爆炸归因）

---

## 零、结论一句话

**能原样照搬的是「小说的规则」，照搬不了的是「小说的身体」。**

- 小说的**机制层**（7 天结算、材料+生存点双轨、每场天灾对应一个建造命题、环形资源依赖、可感知的物理量）—— **全部能实现，而且比 1.0 现在那套更简单**。
- 小说的**内容层**（1653 章的线性叙事、群像、真实社会）—— **照搬不了**。这不是技术问题，是「书是一次性消费品，游戏不是」。

> 所以 2.0 的目标不该是「复刻小说」，而是「**把小说之所以显得合理的那套机制搬过来，然后另造一套能自我生长的内容引擎**」。

---

## 一、先看现状：1.0 差得远不远

| 检查项 | 结果 |
|---|---|
| 现有 NPC / 交易 / 社会系统 | **完全没有**（全项目 grep 无 `npc` / `trade` / `商人`，零命中） |
| 内容模块的实际情况 | `ages.js`（3 个手写阶段）、`endless.js`（9 个模板阶段）、`maps.js`、`gear.js`、`recipes.js`、`items.js` |
| 代码总量 | 约 33.5 万字符（含 UI 的 10 万+） |
| 原著最核心的那一层具备了吗 | **没有**。小说的「房间 / 家具体系」在 1.0 里**一件都没有** |

**好消息**：正因为 1.0 是空白，2.0 要补的东西不需要「拆旧」，属于**纯增量开发**。
**坏消息**：要补的量很大，且**不能再用 `endless.js` 那种 for 循环生成**——那正是用户明确反对的「为了省事用乘法」。

## 二、A 类：能 100% 原样照搬（原著是显式规则，做起来不比现在难）

| # | 原著设定 | 为什么一定能做 | 备注 |
|---|---|---|---|
| 1 | **房间 / 家具体系**：水井、灶台、冰箱、浴室、工作台、装备台、排水渠、通风照明、培养基、床铺 | 纯数据。一张设施卡片 = 功能 + 升级层级 + 耦合关系 | 用户提的全套都在原著里有出处 |
| 2 | **门的三种属性**：防盗 / 防辐射 / 防火 | 一张表三个字段 | 第 2 章就有 |
| 3 | **材质阶梯**：石质 → 混凝土 → 钢铁 → 幽能 → 深渊城兽 | 1.0 已有 `HOUSE_TIERS`，照着扩 | 但要封顶，别推到 30 档 |
| 4 | **双轨驱动**：升级 = 材料 + 生存点 | 两个数值槽，**一行判断而已** | ★ 这是治数值爆炸的关键开关 |
| 5 | **7 天结算一次**，评的是避难所状态不是库存 | 定时 + 一个评分函数 | ★ 第二个开关 |
| 6 | **每场天灾考核一个具体设施命题**（酸雨测防水、暴风雪测保温） | 本质就是：读到城建项 A，比对阈值 | ★ 直接治「abstract 防御数值」 |
| 7 | **箱子等级由获取地危险度决定** | 1.0 已实现（DEVLOG L91） | ✅ 移植即可 |
| 8 | **箱子 = 物资 + 图纸**（厨房/卫生间设计图） | 1.0 已实现（DEVLOG L107） | ✅ 移植即可 |
| 9 | **环形依赖**：造枪需钢 → 炼钢需电 → 发电需矿 | 三条依赖链写成图，引擎一圈扫 | ★ 第三个开关 |
| 10 | **可感知物理量**：7200ml/天、300ml/小时、度、公斤 | 数值本身，不需要引擎改动 | 直接治「1763 亿」这种失感数字 |
| 11 | **复制器思路**：缺某种资源，用*另一种*资源兑换 | 一个兑换表 | ★ 这是替代「乘倍率」的正解 |

> **A 类占了全部要补内容的七成以上。** 换句话说，用户想要的东西，绝大部分是「能做的」——而且是比现在更容易做的。

## 三、B 类：能做，但落地后会长得不一样（必须提前认账）

| # | 原著 | 游戏里会变成什么 | 为什么变形 |
|---|---|---|---|
| 1 | **每 7 天结算** | 变成「**由玩家自己触发的结算**」（攒够了就去申请质评） | 挂机游戏里，玩家可能半夜上线。硬性日历结算容易变成「上线发现被判了一次」 |
| 2 | **每场天灾一次体检** | 体检表必须**提前可见**（玩家要能知道下场考什么） | 小说里主角是「突如其来的挑战」有戏剧性；游戏里未知 = 挫败感，不是惊喜 |
| 3 | **以物换物 / 拍卖 / 世界频道** | 变成**离线 NPC 报价 + 浮动物价表** | 单机 HTML 里没有真人。目前的 1.0 **连 NPC 都没有** |
| 4 | **四条并行支线**（村民群像、异族视角、系统机制、灾变维度） | 压缩成**一张 NPC 关系网 + 好感/敌意轴** | 群像的深度靠笔力不靠结构；AI 能铺量，但难做出「角色让人记一辈子」 |
| 5 | **排行榜 / 千万人竞争** | 变成**影子排行榜**（按公式虚构的其他避难所） | 永远能被识破是纸片人。**但作为「物价/稀缺度」的来源，它反而比真玩家更可控** |
| 6 | **死亡的重量**（角色真的会死） | 变成**不可逆损失，但不是毁灭** | 挂机游戏里玩家会读档/强退，「不可逆」往往是假的。设计成「失去一个人 = 失去一整条配方/加成」，痛但不劝退 |

## 四、C 类：实现不了 —— 这才是问题所在

### C1. 作者的「省略权」（最大的一条）

小说写「**三个月后，炼钢炉终于立起来了**」，是一行字。
游戏里，这三个月**必须真的由玩家一天天过完**。

> 小说的稀缺品是「时间」吗？不是——是**作者替读者承担了所有重复劳动**。
> 游戏没有这个特权：**每一分钟枯燥，都会原样落在玩家的手指上。**

- **替代**：把「重复」本身做成**可优化的对象**。即：玩家的乐趣不是「点了 3000 次」，而是「把 3000 次压到 300 次」。这正是你反对用乘法、而应该用**系统改造**（自动化流水线、设施耦合）来解决的部分——**让玩家在设计，而不是在重复。**

### C2. 「无限升级」这四个字本身就是陷阱 ⚠️

书名里写的是「**无限升级**」，但小说其实 **1653 章就完结了**——它的「无限」是有限章节里的修辞。

**如果游戏真做「无限」，就必须程序化生成新内容 → 程序化生成 = 为了省事用乘法 → 就是你最初抱怨的那件事。**

> 这是一个闭环陷阱：**照搬书名里的「无限」，等于照搬你最讨厌的东西。**

- **替代**：把「无限」改成「**有终点的跃迁**」。原著自己也是这么干的——后期不是材质继续升，而是**避难所 → 地下城 → 文明 → 神域**（整体升维）。五次质变后就到头了，玩家可以转世重开。**有限但有终点的游戏，比假装无限的游戏好得多。**

### C3. 内容产能：1653 章 vs 我们现在有多少

| | 量 |
|---|---|
| 原著 | 658 万字 / 1653 章 |
| 1.0 手写内容 | **3 个阶段**（求生 / 工业 / 能源） |
| 1.0 生成内容 | 9 个模板阶段 —— **已被否决的方案** |

线性补齐剩下的内容，等于要求我们产出几十万字的手写分支。**这是人力问题，不是代码问题，AI 也救不了**（AI 能写，但写的就是模板）。

- **替代：密度替换，不是数量堆砌。**
  与其写 N 条线性剧情，不如写**少量原子 + 组合规则**：

  ```
  手写原子：12 个设施 × 20 个触发条件 × 15 种后果 ≈ 47 个手写单位
  组合结果：理论上数千种局面，每条都对应真实的设施状态变化
  ```

  **关键红线**：后果必须落在**玩家能看见的设施/物资/关系**上。
  只要后果是真实的（冰箱真的不制冷了），组合就不会退化成「换名字」——因为每种组合玩家的应对真的不同。

### C4. 主角的天才 vs 玩家的普通

苏摩是前理工科毕业生、理性主义实践者，**他的「正确的直觉」是作者事后追认的合理性**。
游戏里，玩家没法自带天赋——**一切必须先把决策写成可判定规则**。

> 推论（很重要）：**2.0 不能设计「只有天才才解得开的题」。** 所有谜题必须是「信息给足了，愿意思考就能解」。

- **替代**：把难度放在**信息不完整**上（要不要派侦察队去探未知区域），而不是放在**智力门槛**上。

### C5. 节奏控制权在谁手里

小说由作者决定什么时候给爽点。游戏是玩家自己决定什么时候玩——
**玩家可能在最枯燥的采集期一口气玩 8 小时，体验直接崩掉。**

- **替代**：靠**结算锚点**（每 7 天一次评级）人为切出节拍；外加**离线托管**，把重复劳动放进「离线结算」，回到玩家手上的只有决策。这正好和挂机游戏的长处对上。

## 五、给 2.0 的红线（建议先立，防止中途走偏）

1. **不许为了填满内容而用模板生成** —— 这是 `endless.js` 的教训，也是用户最初抱怨的根源。宁可内容少、阶段有终点，也不要假无限。
2. **数值必须从属于设施状态** —— 资源是耗材不是分数（对应 C2 / A5）。一旦又开始比谁库存大，就回到 1763 亿。
3. **一切产出提升只能来自「系统结构的改变」，不能来自「同一个数字乘上一个系数」** —— 想让产出变多的唯一正当理由是：你多造了一套东西、打通了一条耦合、解锁了一种兑换。**不可以是该设施升了一级所以 ×2。**
4. **不许存在「全局清单」**（2026-09-27 追加，★ 用户口径更正后的版本）—— 东西挂在世界的**位置 / 事件 / 人**上，
   而不是挂在等着被解锁的总表里。**「解锁」这个词本身要废弃，改成「发现」**。
   已知/风闻/未知是存档里的认知状态，不是渲染时的过滤开关。配套安全阀见 6.5。

## 六、信息的可见性 —— 用户明确反感「还没拿到就全摆在那」

> 用户原话（2026-09-27）：「**我很不喜欢 1.0 的那种还没获得就全在那摆着的玩法**」
> **用户随后的口径更正**：「重点不是告诉我缺什么材料，重点是**很多东西直接摆在明面上**这个设定。」

### 6.0 ⚠️ 口径更正（很重要，别再往下记错）

我在第一轮把这条记成了「UI 显示得太详细 / 连攻略一起给」—— **那是次生现象，不是重点。**
用户在下一条消息里明确纠正了：**他反感的是「这些东西的存在被预先展示」这个设定本身。**

两者的差别，决定了改法的差别：

| 误解版（我最初的理解） | 正确版（用户的意思） |
|---|---|
| 毛病是**显示得太详细**（花费、日程、去哪采都写出来） | 毛病是**这些东西的存在先被摆出来了**，细不细只是放大器 |
| 改法：把 UI 折叠、少写点提示 | 改法：**根本不该存在一张全局清单** |
| 层面：UI / 交互优化 | 层面：**世界观 + 数据结构** |

**一句话讲清本质差别：**

> **「解锁」= 东西早就在那儿，我只是暂时不给你权限。**
> **「发现」= 它在某个地方，你还没走到过那儿。**

1.0 做的是前者，所以玩家从第一天起就知道世界上有什么，剩下的只是在打勾；
用户要的是后者 —— **世界里的东西应该自己待着，不主动列队报到。**

### 6.1 现状实证（grep 出来的）

| 位置 | 证据 |
|---|---|
| **建筑面板** `ui.js:467 renderBuildings()` | 遍历 `BLDCFG`（**全局建筑表**）全部条目；未达门槛的照样占位，按钮写「需〈具体名字〉」（L512）。第 5 阶段的「深井改造」在第 1 天就在列表里 |
| **制作面板** `ui.js:1209` | 遍历全局配方表；无图纸的折成 `❓ 未知图纸 ×N` —— **「还有 N 个」本身就在泄露存在性** |
| **地图** `ui.js:1787` | 无迷雾；地点取自全局 `SPOTS` 表，没去过也看得见、能排班 |

> 注意共同点：三处的渲染入口都是「**遍历一张全局表**」。
> 只要数据结构是全局表，"全摆着"就是**必然结果**，不是 UI 的疏忽。

### 6.2 由此得出的架构结论（★ 这决定了 2.0 怎么搭）

**1. 不许有「全局清单」这种数据结构。**
一件东西应该挂在**世界的位置 / 事件 / 人**上，而不是挂在一张等着被解锁的总表里。
任何形如 `ALL_X.map(...)` 的渲染都应该消失 —— UI 只画**已经在玩家认知里的东西**，
这里不存在"过滤"，因为**没有东西可以被过滤**。

**2. 「已知 / 风闻 / 未知」不是一个渲染开关，是存档里的真实状态。**
玩家的「认知」是一个被持久化的集合（知道了什么、听谁说的、在哪儿听说的），
不是渲染时临时算出来的 `player.lv >= X`。

**3. 因此 2.0 必须有真实空间，否则没地方"放"东西。**
「走到那儿才发现」要求地图有坐标、距离、可达性、视线。
**这一条把「地图迷雾」从可选特性升级成了地基工程** —— 它不再是 UI 效果，而是承载内容的容器。

**4. 只在 UI 层藏 = 假藏。**
过滤条件一旦写漏、或被后续版本绕过，整张表立刻露馅。藏必须在源头。

### 6.3 对照例子（同一个「深井」，两种写法）

| | 1.0 的写法 | 2.0 的写法 |
|---|---|---|
| 第 1 天 | 建筑列表里就有「深井改造」，写着需「幽能」 | 玩家认知里**不存在这个词** |
| 什么时候出现 | 达到 lv 条件自动亮起 | 派出去的人在某片区域踩到一处空洞，日志里蹦出一句「地面下面是空的」 |
| 之后 | 满足条件点按钮 | 玩家得决定要不要挖、派谁、带什么 —— 而工具不够就只能先记着 |

### 6.4 让东西进入认知的四条途径

1. **亲眼看见** —— 探索队在某个坐标真的碰上了（最重要，且必须要有地图承载）
2. **需求倒逼** —— 缺水到一定程度，才会想到"能不能往下挖"
3. **听人说的** —— NPC / 图纸 / 用东西换来的情报
4. **玩家自己提案**（★ 最有价值）—— 玩家输入「我想试试 XX」，系统判定行不行。从根上消灭列表

### 6.5 ⚠️ 安全阀（不做会直接毁掉游戏）

**隐藏的前提：绝不能因为「不知道某个选项存在」而永久卡住。** 三条兜底：

1. 需求倒逼会兜底 —— 缺到一定程度会提示，把玩家推向正确方向
2. NPC 会兜底 —— 卡住超过 N 天，有人来提一句
3. 不许存在「只有唯一解、且必须先知道某个秘密才能发现」的死锁

> **隐藏是为了让发现有价值，不是为了为难人。**

### 6.6 与原著的对照

原著里苏摩是**慢慢知道世界上有什么的** —— 第 3 章才知道饮水是个问题，第 50 章才见到完美设计图。
1.0 反过来：**玩家开局就知道全部，只是权限不足。**
这正是**搬运小说设定时最容易丢失的那一层** —— 不是清单的内容抄错了，是**用清单代替了世界**。
